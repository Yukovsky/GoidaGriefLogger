# Состояние GoidaGriefLogger

**Версия:** 3.2.0 · **mod_id:** `goidagrieflogger` · **пакет:** `com.gle.*`
**Платформа:** Minecraft 1.21.1 · NeoForge 21.1.228+ · Java 21 · только сервер

GoidaGriefLogger — форк и поглощение [GriefLogger](https://github.com/daqem/GriefLogger) (Apache-2.0):
один мод, одно соединение с БД, одна очередь записи на все события. GriefLogger помечен
в `neoforge.mods.toml` как `incompatible` — вместе они не запускаются, оба заняли бы `/gl`.

История изменений по версиям — в [CHANGELOG.md](CHANGELOG.md). Здесь только текущее устройство
и то, что осознанно не сделано.

---

## Устройство

### Запись

Единственный писатель: `GLStorage` держит соединение (`GLDatabase`), очередь (`WriteQueue`)
и все DAO. Порядок старта важен и зафиксирован: миграция схемы выполняется **до** запуска потока
записи, потому что `Connection` не потокобезопасен.

`WriteQueue` группирует пакет по SQL, готовит один `PreparedStatement` на таблицу и отправляет
строки одним `executeBatch()`. Задача не исполняет запросы сама — она берёт statement у пакета
(`StatementSink`) и делает `addBatch()`. Это позволяет одной задаче писать в несколько таблиц
(`SessionDao`) и строить SQL по живой схеме (`TextLogDao` определяет имя колонки по БД).

При переполнении очереди запись не отбрасывается сразу: сначала короткое окно на дренаж
и только потом отбрасывание со счётчиком. Остановка дожидается выхода потока из текущего пакета,
прежде чем закрыть соединение.

### Кэши

- `IdCache` — `name → id` для `materials`/`levels`/`entities` и `uuid → id` для `users`.
  Вставка в справочник идёт только при первом появлении имени.
- `NbtStore` — снимки NBT, адресуемые содержимым: `hash → id`, одинаковые снимки лежат один раз.

Оба живут на потоке записи и сбрасываются хуком `WriteQueue.setOnRollback` при откате пакета —
откат мог отменить вставку, которую кэш уже запомнил.

### Захват событий

| Что | Чем ловится |
|---|---|
| Слом/установка/взаимодействие игроком | события NeoForge (`PlayerBlockListener`, `VanillaInteractListener`) |
| Прямая установка блока без событий | `LevelChunkMixin` на `setBlockState` |
| Атрибуция не-игровых изменений | `GriefContext` (стек на потоке) + `GLESourceResolver` |
| Содержимое контейнеров | снимок при открытии, разница при закрытии; доступ — через `ContainerAccess` |
| Собственная работа машин | `MachineTickMixin`, `BrewingStandTickMixin` → `MachineActivity`, вычитается из разницы |
| Перемещения предметов автоматизацией | `BlockCapabilityMixin` оборачивает `ItemHandler` → `AutomationItemLogger` |
| Убийства сущностей | `LivingDeathEvent` + снимок через `EntityNbt` |

`ContainerAccess` — единая точка получения предметного хендлера для логирования И отката. Оба
пути обязаны видеть контейнер одинаково, иначе откат применяется не к тому, что писалось.
Выбирается полнейший вид: у двойного сундука это объединённые 54 слота, а не 27 одной половины;
у модовой машины, публикующей хендлер только по граням, — `Container` самой блок-сущности.

### Откат и restore

Откат возвращает территорию к снимку на момент `timeFrom`: обратные операции применяются
от новых записей к старым, поэтому последней применяется самая старая — она и задаёт результат.
Restore — строго обратная операция: те же действия проигрываются заново, от старых к новым.

Строки выбираются с предикатом `rolled_back` (`0` для отката, `1` для restore) и помечаются
по **фактически применённым** id, а не по всему фильтру. Строка, для которой применение
не удалось, остаётся непомеченной и попадёт в повторную попытку. Отказ сообщает причину
с координатами, а не только счётчик.

Превью показывает тот же итог, что даст откат, и обводит область рамкой из партиклов,
отправляемых лично инициатору — мод остаётся серверным.

## Осознанные ограничения

Это не баги, а известные границы. Каждое стоит держать в голове при разборе инцидента.

- **Собственный расход модовых машин не вычитается.** Учёт написан для ванильных печей,
  коптилен, доменных печей и варочных стоек. У модовой машины её переплавка может приписаться
  игроку, державшему GUI открытым. Ошибка в сторону лишней записи, не пропуска: спрятать
  предмет нельзя. Обобщается перехватом тика любой блок-сущности.
- **Хопперы логируются как `[AUTO]`, а не `[HOPPER]`.** Ванильный путь
  `HopperBlockEntity.addItem` в NeoForge практически не достигается — реальные переносы уходят
  раньше через capability. Перехват работает на capability-пути, где механизм-инициатор уже неизвестен.
- **Транзакция внутри одной сессии не видна.** Положить и забрать при одном открытии контейнера
  даёт нулевую разницу. Ничего при этом и не спрятано: состояние не изменилось.
- **Таблица `items` не откатывается.** У неё нет колонки `rolled_back`; подбор, выброс и крафт
  фиксируются, но откату не подлежат — «отменить подбор» не имеет однозначного смысла.
- **Рамки и картины выключены по умолчанию** (`enableItemFrames = false`). Механизм есть,
  включая атрибуцию установки реальному игроку.
- **Установка стойки для брони не логируется**, хотя её разрушение фиксируется: `ArmorStand`
  это `LivingEntity`, и разрушение ловит `EntityKillListener`. Асимметрия известна.
- **Рюкзак, открытый из инвентаря, а не как блок,** не покрыт: у него нет позиции в мире,
  а весь контейнерный слой построен вокруг координаты блока.
- **Модовые «стоячие» сущности** (мольберты, стойки и подобное) не логируются при установке.
  Обобщается корреляцией появления сущности с недавним правым кликом игрока — механизм для этого
  уже есть, он используется для рамок.

## Проверка

```bash
sh tools/selfcheck.sh
```

Поднимает настоящую схему через `SchemaMigrator` во временной SQLite и гоняет настоящие запросы
и запись. Покрыто то, что ломается молча, а не громко: предикат `rolled_back`, порядок привязки
параметров, порядок применения для отката против restore, симметрия цикла откат↔restore,
пакетная запись, дренаж очереди на остановке, дедупликация NBT, отрисовка откатанных строк.

Скрипт пересобирает исходники перед прогоном — иначе проверки шли бы по устаревшим классам.

Остальное требует живого сервера: применение к миру, миксины, партиклы, модовые блоки.

## Сборка

```bash
./gradlew build
```

Результат: `build/libs/goidagrieflogger-<версия>.jar`. Драйверы SQLite и MySQL встроены
через `jarJar`.

Тег вида `v*` запускает workflow `Build & Release`, который собирает jar и публикует релиз.
